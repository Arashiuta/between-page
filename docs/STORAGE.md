# 数据存储与恢复

数据目录是可整体复制和备份的独立单元。默认位于项目或便携程序旁的 `data/`；修改存储位置后，以「设置 → 软件设置」中显示的路径为准。程序旁的 `data-location.json` 只负责定位自选目录，不保存故事内容。

上传的 TXT／Markdown 原始文档仅在资料编辑会话内用于 AI 提炼，不写入数据库或素材目录。保存资料仅保留概述、规则、分区要点与参考图关联；资料库引入副本记录来源 ID 并保持只读。

## 目录约定

| 位置                        | 内容                                                       | 内置备份 ZIP       | 更换数据目录     |
| --------------------------- | ---------------------------------------------------------- | ------------------ | ---------------- |
| `data-layout.json`          | 目录格式版本，当前 `formatVersion: 2`                      | 包含（存在时）     | 包含             |
| `database/storybook.sqlite` | 正文、设定、记忆、版本、草稿、图片索引、应用配置和 API Key | SQLite 在线快照    | SQLite 在线快照  |
| `assets/`                   | 所有持久素材，按类型与用途划分                             | 递归包含所有类型   | 递归包含所有类型 |
| `settings/`                 | 预留独立配置文件；当前软件与模型设置仍在数据库中           | 包含               | 包含             |
| `backups/`                  | 历史备份 ZIP、升级前的自动备份                             | 排除，避免递归打包 | 保留             |
| `exports/`                  | 用户主动导出的副本                                         | 排除               | 保留             |
| `runtime/`                  | Electron 会话、缓存、日志和 `tmp/` 暂存文件                | 排除               | 重建             |

素材当前使用以下结构，每张图片以 `<图片ID>.<扩展名>` 命名：

```text
assets/
└── images/
    ├── references/
    │   ├── library/                        # 资料库上传的参考图
    │   └── stories/<故事ID>/               # 故事中上传的参考图
    └── illustrations/
        ├── stories/<故事ID>/               # 故事生成的插画
        └── library/                        # 兼容没有故事归属的历史插画，按需创建
```

故事 ID 和图片 ID 不随名称变化，避免名称重复、非法文件名或故事改名影响读取。章节、版本、人物与参考图之间的关联由数据库中的 ID 保存，不通过文件名推断。

一张图片可以被多个角色、资料库条目或故事引用。目录表示初次存储的位置，后续共享、复制设定或删除故事不会随意搬动文件。彻底删除故事时，只逐张移除无外部引用的专属图片；共享图片继续保留在原路径，不能直接递归删除该故事的素材目录。

## 路径与写入

- `ImageAsset.filename` 保存相对于 `assets/` 的路径，统一使用 `/`。界面通过图片 ID 请求内容，绝对磁盘路径不写入资料引用，复制数据目录后仍可读取。
- 主进程通过统一的素材读写入口解析路径，拒绝绝对路径、`..`、Windows 特殊路径，以及素材树中的符号链接和目录联接。目录初始化、备份和迁移也拒绝目录联接，避免复制或操作数据目录外的文件。
- 新图片先写到 `runtime/tmp/`，写完后重命名到最终位置，再保存数据库索引。同名文件不会被覆盖；数据库保存失败会清理本次新写入的图片。
- 进程异常结束可能留下临时文件，或留下写入成功但尚未登记的素材。它们不会被当作正式索引，也不会自动删除未知文件；彻底退出软件后可清理 `runtime/tmp/`。持久素材的自动垃圾回收暂不启用，避免误删尚需恢复的文件。

文件写入与 SQLite 事务不能组成单一跨系统事务，因此按“先保留文件，再提交引用”的顺序处理；迁移前还会保存可恢复的快照。不要在软件运行时手工重排、删除或同步覆盖数据库和素材。

## 旧数据升级

未带目录版本文件的数据按旧结构识别。新版启动后，在打开工作区之前执行：

1. 检查目录版本；版本损坏或高于软件支持范围时停止打开，保留原内容。
2. 遇到可迁移的旧图片时，先在 `backups/` 生成数据库与素材 ZIP。备份失败则停止迁移。
3. 根据数据库中的图片用途与故事 ID 计算新路径。复制文件后再更新该图片记录，图片 ID 及所有引用保持不变。
4. 同一旧文件被多个图片记录共用时，等这些记录均已迁移后再移除旧文件。
5. 已存在的目标文件必须与原图内容一致，才能继续中断的迁移；冲突时停止并保留原文件。缺失图片保留旧路径及记录，并在启动日志中列出 ID，补回原位置后再次启动即可重试。
6. 写入目录版本文件。每次启动仍检查遗留的平铺记录，兼容旧备份恢复或补回缺失文件的情况；没有登记在数据库中的旧文件保持原样。

自动备份不包含运行缓存、导出副本和已有备份。升级前若希望保存整个目录的原貌，可彻底退出软件后自行打包数据目录。需要回退旧程序时，使用升级前的同一份备份恢复，避免让旧程序继续修改新版数据。

## 备份、恢复与搬迁

「创建备份」使用 SQLite 在线快照并递归加入持久素材与配置文件。备份期间暂停其他应用操作；若有生成任务或尚未完成的文件操作，会提示先等待完成。ZIP 完成后才使用正式 `.zip` 文件名，失败的 `.partial` 不作为成功备份。

恢复时彻底退出程序（包括系统托盘），先保留现有数据目录副本，再将同一份 ZIP 解压到一个新的数据目录。不要把数据库覆盖到仍带旧 `-wal`、`-shm` 的目录中，也不要混用不同备份中的素材。新旧格式的备份均可由新版打开，旧图片目录会自动整理。

默认数据位置可直接把新目录作为程序旁的 `data/`。使用自选位置时，确保程序旁 `data-location.json` 的 `dataDir` 指向恢复后的目录；跨电脑时原绝对路径可能不可用，需要更新定位。

「更换目录」要求选择一个独立空目录。先在目标的暂存目录生成数据库快照并复制素材、配置、历史备份与导出文件，复制完成后才更新定位并重启；原目录保留。运行缓存重建，素材索引使用相对路径，无须重写数据库中的磁盘路径。

若希望同时保留缓存、所有历史备份和导出文件，完全退出后直接打包整个实际数据目录即可。手工导出到数据目录外的文件需要另行备份。API Key 明文存放在数据库中，备份中也会包含。

## 扩展约定

未来新增文档附件、音频或其他图片用途时，遵循 `assets/<素材类型>/<用途>/<作用域>/<稳定ID>.<扩展名>` 的路径规则，按需创建目录。当前没有实现音频或文档附件存储，不提前堆放空目录。

新增持久素材应继续使用统一路径校验和相对路径引用；新增图片用途时扩展用途映射。现有备份和迁移会递归包含整个 `assets/`，无需为每种素材单独增加复制分支。预览图、缩略图和可重新计算的索引应放入 `runtime/`，与原始素材分开。

以后若改变既有目录规则，应增加目录格式版本，并提供可备份、可重试的迁移。数据库表结构版本与目录格式版本分别管理；`data-layout.json` 不承担图片索引或应用配置职责。

## 工作台领域数据

数据库结构版本保持为 2，本次更新直接复用已有数据库，无需重建。额外设定与大纲共用节点列表，按类型隔离操作及版本恢复，保留节点 ID 与章节关联。对话、实际来源快照与统一修改建议分别持久化；走向及其独立来源快照按故事和章节保存在 settings，下一章记录来源与最终写作要求。采用在主进程事务内保存审核快照、更新内容及记录采用状态。界面暂存和候选展开状态按故事保存，对话再按创作模式和目标隔离。早于版本 2 的开发数据库仍由原有格式检查拒绝；目录布局升级与领域数据库格式是独立机制。
